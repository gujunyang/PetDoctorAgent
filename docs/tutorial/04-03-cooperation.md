## 核心结论

- 本项目是集中调度、外层顺序路由、共享状态交接；未实现专家并行讨论、投票或相互辩论。
- 外层图管理专家节点顺序；问诊/推荐内部 Agent 管理工具使用。专家数量、模型种类、实际模型请求次数是不同指标。
- 模型组件统一通过 get_llm 创建客户端，通常读取同一套配置；不同角色主要由指令、输入、工具和输出契约区分。
- 病历 Worker 是确定性节点，无内部 LLM；安全 Worker 混合规则与模型。不能把每个 Worker 都理解为同一种模型循环。
- 问诊结果经外层 State 交给后续推荐/安全使用；用户看见的回复由入口选择，当前不是自动汇总所有专家答案。

## 模块分工

| 模块 | 本项目执行方式 |
|---|---|
| Supervisor | 新回合模型路由与固定分支结合 |
| 问诊 | 预检索、工具 Agent、结构化抽取 |
| 推荐 | 工具 Agent、结构化抽取 |
| 安全 | 关键词命中直接输出，否则调用模型审查 |
| 病历 | 读取状态，按条件直接调用工具，代码格式化回复 |

## 协作路径示例

假设身份已确定、抽取成功且首轮无旧安全标记，第一轮问诊可走：

```text
用户问题 → 调度 → 问诊 → 状态更新 → 调度 → 安全 → 本轮结束
```

用户下一轮请求产品时，可走：

```text
新消息 + 已保存状态 → 入口/身份步骤 → 调度 → 推荐读取已有诊断 → 调度 → 按状态继续或结束
```

两条都是教学推演，非实测。第二轮可能受旧 safety_flag 影响而结束，不能画成必然再次安全审查。推荐也可从用户直接产品诉求进入，无强制先问诊要求。

病历路径（已到达调度且选中病历）：

```text
调度 → 病历节点读取档案与历史 → 可用时查询演示病历工具 → 格式化 → END
```

节点内部没有模型调用，不代表整条请求没有模型调用：此前身份提取与意图路由仍可能使用模型。

## 设计取舍

- 好处：职责、工具和输出更明确，便于分别观察、修改提示词和设计回归用例。
- 成本：增加路由和抽取调用，产生更多状态衔接和失败分支；延迟、用量需实际测量，不能仅凭 Agent 数推算。
- 同一模型的多个角色可能共享错误倾向；分工不等于独立验证，更不保证结论正确。
- 多 Agent 不必须如此设计；单 Agent 多工具、并行专家等是其他可能方案，未在当前项目实现，不在本章展开。

## 易混淆点

- 模型输出工具请求后，由框架/程序执行工具，不是模型自己直接访问数据库。
- 对外层 State 有字段访问能力，不代表模型本次收到所有字段；也不构成强权限隔离。
- 病历补全 profile 在 record_node 中用于本次显示，没有因此自动调用长期记忆保存函数。
- 安全节点直接结束；普通问诊/推荐先回调度；病历也直接结束。没有统一的“专家全答完再综合”节点。
- 用户没有明确确认理解，三节均保留已讲解／答疑中。
